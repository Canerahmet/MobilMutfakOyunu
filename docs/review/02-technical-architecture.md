# Review 2: Technical Architecture

**Perspective:** lead engineer who has shipped several Unity mobile games and run at least one Steam port
**Items owned:** B3, B4, B5, B6, B7, A11
**Date:** 9 September 2026

---

## Overall assessment

The plan starts in the right place: a core boundary enforced by the compiler, a balance harness on the console as Phase 0, and decisions such as "no manual saving" are the highest-return decisions there are on a one-person project. But determinism, the plan's load-bearing claim (04 §The outer face of the core; 15 §Seed), is not yet a design, it is a wish: the `Tick(deltaTime)` signature, where the RNG lives, floating-point state and the tr-TR culture are unwritten, and each of them invalidates the save system and the balance harness together in month six. The data schemas cannot express three of the four signature mechanics, nor the staff capacity model. On the render side, the GPU Resident Drawer is the wrong tool for this scene. The five problems below are cheap right now; they must be closed before Phase 0.

## The three strongest things

1. **A boundary the compiler enforces, and Phase 0.** Turning Unity references off in the `Lokanta.Core` asmdef (04 §The compiler enforcing the layers) and writing the balance harness before touching Unity (04 §Headless balance harness) prevent the UI-simulation mixing that is this genre's most common form of rot, from the start.
2. **The save principles.** No manual saving, atomic writes, `.bak`, a checksum, migration functions that are never deleted, asking the player instead of merging, no encryption (15 §Protection against corruption, §Version migration, §Cloud save; 19 B6). All of them right, and all of them argued for.
3. **Content and measurement discipline.** Immutable `id`, a localisation key, a validator that rejects at start-up (13 §Principle, §Validation); profiling only on device, a budget overrun resolved before a feature (19 B5 §Measurement); simple staff AI (14 §Staff AI) is a friend of determinism too.

## The five riskiest problems

### 1. Determinism is not designed; the save system and the balance harness lean on it

**The problem.** `sim.Tick(deltaTime)` (04 §The outer face of the core) lets Unity's variable frame time into the core. Two playthroughs with the same seed see a different `deltaTime` sequence; every accumulation such as `patience -= dt` diverges and the claim that "state plus seed reproduces the day exactly" (15 §Seed) falls. There are four more unwritten traps: (a) the RNG is undefined; you cannot trust Unity's Mono/IL2CPP BCL and the harness's .NET 8 `System.Random` to give the same sequence, and fast-forwarding by "the number of steps consumed" is a poor proxy for saving the internal state. (b) Three different code generators (IL2CPP ARM64, Mono, RyuJIT) do not guarantee the same floating-point result; `Math.Sin/Exp` depend on libm. (c) `Dictionary`/`HashSet` ordering and the instability of `List.Sort`. (d) The tr-TR culture: `"izgara".ToUpper()` is "İZGARA" in the Turkish culture and `double.Parse("0.15")` gives a different result; the development machine is Turkish.

**Why it matters.** Mid-service saving, debug replay and the outputs of Phase 0 all depend on the same assumption. The divergence shows up in month six as a "loading the save gives a different day" bug, and the cause cannot be found.

**The fix.** A fixed step: a parameterless `Tick()`, a 100 ms step; the Application layer accumulates real time and calls the step (with an upper bound per frame), and the save keeps a `tickIndex`. State entirely integer: money already is, times in milliseconds, satisfaction and reputation in 1/100 points, quantities in grams (13 §The answer to pending decision 1). All of the formulas in 12 §5 are addition, multiplication and division; there is nothing exponential or trigonometric, so moving to fixed point is free and rounding is defined in one place. Its own RNG in Core: xoshiro128** or PCG32, state serialised, a separate stream per subsystem and per day (`SplitMix64(campaignSeed, day, streamId)`); that way a call added to one system does not shift another, and a single day can be replayed without winding through 59 days. `string.GetHashCode` banned; ties broken by `id`; CA1304/1305/1307/1309 at error level in the Core csproj; `CultureInfo.DefaultThreadCurrentCulture = InvariantCulture` at start-up. A CI test that runs the same seed on .NET 8 and on Android IL2CPP and compares the end-of-day state hash; the hash is also written into the save envelope.

### 2. Three seams of the core boundary are empty: serialisation, events, composition

**The problem.** The diagram (04 §The compiler enforcing the layers) does not say where the JSON library lives; there is no `JsonUtility` in Core and `System.Text.Json` is not built into Unity. There is no mechanism for "the core raises events" (04 §The event flow is one-way); a class-typed `event Action<T>` allocates garbage on every event and breeds subscription-lifetime bugs. An assembly that goes `Platform.Mobile → Ports` cannot bind itself to `App`; the composition root is undefined. The `Ports → Core` dependency is unnecessary. How the harness compiles Core's sources is unwritten: .NET 8 accepts C# 12, Unity 6 stays on C# 9; one day the code will not compile in Unity.

**The fix.** Core: types, rules, DTOs (`SimEvent`, commands, `DayReport`, a state snapshot), zero dependencies. Content: the JSON→Core loader and validator, Newtonsoft (`com.unity.nuget.newtonsoft-json`, the same NuGet in the harness). Save: the envelope and the migrations, Newtonsoft. App and the harness both reference the pair. Events: a `readonly struct SimEvent { kind, tick, id1, id2, value }` accumulates in a list and App drains it after each step with `DrainEvents(buffer)`; zero allocation, and loggable for replay. Content ids are strings in JSON and are converted to a `DishId(int)` struct on load; the save writes strings. Ports use only `byte[]`, strings and their own small DTOs, and do not depend on Core. `Lokanta.Boot.Mobile`/`Boot.Steam` (referencing App + Platform.*, filtered with the asmdef's `includePlatforms`) becomes the composition root. On the harness side `Lokanta.Core.csproj` pulls in the same `.cs` files with `<Compile Include>`; `netstandard2.1` and `LangVersion 9` are pinned.

### 3. The schemas cannot express the signature mechanics or the capacity model

**The problem.** There is no schema at all for the free cuisine's signature mechanic, the combo (07 §Fast food; 12 §3). `signatureMechanic: "veresiye"` is a single string (13 §cuisines.json); the tab's repayment probability, delay and cap (07 §Turkish cuisine, "who will pay is uncertain"), the portion cost and range of the Japanese soup stock, and Italian courses and table times are absent. The claim that "cuisines differ only as data" (07 §Its risk) is wrong for the signature mechanics; each of them is code, and there is no parameter block. 14 §Capacity model's capacities of 16/20/26/34, the 70%/45% diminishing returns, the 50% off-role figure, the owner's 12, the maximum staff per tier, 30 points per level, the raise demand, severance: none of it is in `staff-roles`, `expansions` or `economy.json`. Trait conditions ("in busy slots", "in the last quarter") cannot be written as a plain `effects` number; the keys are free strings and the validator (13 §Validation) does not check them. `hourSplit` (cuisines) and `arrivalWeights` (archetypes) are two sources for the same thing; 12 §5.6 makes it per cuisine. The dish-of-the-day discount and the cost of tea (12 §3) are missing. `spoilDays` is day-granular; the "freshness counters" in 15 and the Japanese fresh ingredient want an intra-day curve.

**The fix.** `combos.json`; `cuisines.signature: { kind, params }` as a discriminated union, with a typed parameter class in Core for each `kind`; `staff-roles.dailyCapacity`, `expansions.maxStaff`, `economy.staffing { stationDiminishing, offRoleEfficiency, ownerCapacity, xpPerLevel, raiseDemand, severanceWeeks }`; a `TraitEffect` enum and a `condition` field for `effects`; a `conflictsWith` symmetry check; `hourSplit` collapsed to a single source. The `id` rule gains "never deleted, retired with `deprecated: true`". A JSON Schema file for every schema (so that AI-generated content errors show up immediately in the editor) and the validator in CI under `dotnet test`. Rejecting at start-up is right for local content and wrong for a downloaded pack: the pack is quarantined and the game opens.

### 4. Mid-service saving: a full snapshot every ten seconds, on the main thread

**The problem.** 15 §What is saved both says "state plus seed is enough" and asks for the live state of tables and orders. If the snapshot path is chosen, producing up to 200 KB of JSON every 10 s (15 §When), gzipping it, checksumming it and fsyncing it on the main thread means a 10-30 ms hitch; flash wear is not the problem, the hitch is. The write order (19 B6 §File layout) does not say `Flush(true)`; a rename without fsync leaves a zero-length "valid" file after a power cut. The envelope (15 §Version migration) does not carry `savedAtUtc`, device name, play time, `tickIndex`, content version or a state hash; the conflict dialog (15 §Cloud save) is built out of exactly those. iCloud key-value storage is 1 MB in total; 4 slots × (`.save` + `.bak`) may not fit.

**The fix.** Mid-service save = a start-of-service snapshot + a command log + `tickIndex`. Stations do not change during the day (14 §Station assignment) and there are at most 4 interventions a day (13 `interventionsPerDay`); that is a few hundred bytes per day. On load it is replayed and the hash at the target tick is compared with the one in the envelope; on a mismatch it falls back to the full snapshot (both are written until problem 1 is proven). The main thread only produces the byte array; gzip + CRC32 + `Flush(true)` + `File.Replace` happen in a `Task`. On being backgrounded, a synchronous and small write inside `OnApplicationPause(true)`. On a conflict, the losing save is kept as `slot_N.conflict`. CloudKit or iCloud Documents on iOS, Play Games Saved Games on Android (3 MB per snapshot); the cloud carries a single gzip blob per slot. An `IStoreFront` ownership check when a slot is opened; ownership is not kept in the save file.

### 5. The GPU Resident Drawer is the wrong tool; baked light contradicts the layout mode; the budgets are not measurable

**The problem.** The GPU Resident Drawer (19 B4 §Settings) requires Forward+ in URP, runs on top of `BatchRendererGroup` and does not exist on OpenGL ES; that is, it is disabled on the fallback GLES 3.1 devices — exactly the lowest devices that were promised 30 fps. `SkinnedMeshRenderer` (customers, staff) and UI are out of its scope. Its benefit shows at thousands of instances; at 100 draw calls it cannot be measured, and in exchange you pay GPU memory and the cost of Forward+ clustering. "Furniture baked" (19 §Lighting), but B7 has a Layout map and 15 has a "floor plan": if a table can be moved, its light cannot be baked; a lightmap set per expansion tier × cuisine environment eats 200 MB. The budgets are in counts, while the cause of a hitch is milliseconds and garbage: there is nothing on per-frame GC, Canvas rebuilds (TMP numbers changing every frame) or UI overdraw; there is a "no thermal throttling for 30 minutes" goal (19 B5) but no instrument for it (Adaptive Performance); the memory measure (PSS or Unity reserved?) is undefined. Linear + MSAA at 60 fps will heat a mid device.

**The fix.** GRD off; Forward, SRP Batcher + static batching + GPU instancing on the chair/plate materials is enough; revisit if a profile shows the render thread is the bottleneck. HDR off, MSAA 4x (cheap on a tile GPU), a Render Scale setting. Bake walls and floor only, furniture on probes plus a single directional light. Budgets in ms on the lowest device: main thread ≤ 10 ms, render ≤ 6 ms, GPU ≤ 14 ms; 0 B/frame GC during service; dynamic text on a separate Canvas; memory as `dumpsys meminfo` PSS ≤ 500 MB. 60 fps only on the top tier, `Application.targetFrameRate` + Adaptive Performance (ADPF). ARM64-only build. One GLES 3.1 device mandatory in the test matrix. Addressables as local groups in the first release; the remote CDN burden (hosting, catalogue versioning, a download failure → a refund) is not taken on unless the measured size exceeds 200 MB (19 §Pending decision 4).

| B5 Performance targets | REVISE | Count budgets must become ms/thread budgets; GC, Canvas, overdraw, a PSS definition and Adaptive Performance must be added; 60 fps must be limited to the top tier; remote Addressables must be deferred past the first release (problem 5). |
| B6 Save file format | APPROVE | JSON + gzip + checksum + unencrypted + `.bak` is right. Conditions: write down the checksum algorithm (CRC32 or xxHash32), `Flush(true)` + `File.Replace`, meta fields in the envelope, Newtonsoft, migrations over an untyped JSON tree, a test fixture for every version. |
| B7 Input action map | REVISE | On desktop, Esc is both Pause and Cancel, and left click is both Select and Intervene (19 B7 §Actions); map priority is undefined. 04 §The input layer includes the gamepad under Desktop, 19 B7 says "not in the first release"; a contradiction. The gamepad scheme must be added to `.inputactions` now: Steam Deck "Verified" requires full controller support, and 16:10 (1280×800) breaks the "16:9 and wider" assumption (04 §Aspect ratio). There is no `Inspect`/long-press equivalent for hover. `IInputSource` should not be a port: a scheme is not a build target but a runtime capability (touch on the Deck, a mouse on Android) and the Input System already switches schemes. "No precise aiming" is right; a "select-confirm" equivalent must be added for "drag" so that controller and touch follow the same flow. |
| A11 Save system design | REVISE | Slots, locking, atomic writes, migration, asking on a conflict approved. Mid-service saving must be a command log + replay, the write must move to a background thread, the envelope needs meta fields, the losing save must be kept, the cloud back end must be chosen with the size limits in mind, ownership must come from the store (problem 4). 15 §Pending decision 4: keep asking, with the newer one preselected. |

## Unanswered questions

1. Which JSON library, in which assembly? Which .NET version is the harness on, which C# version is Core pinned to? 04 §The compiler enforcing the layers does not say.
2. What does `IAdProvider`'s "rewarded ad" (04 §Ports) reward? There is no definition in the documents I read; unless there is a use that does not contradict "no power sold, no timers" (07 §Why this structure is right), the port must go, as 04 §Over-engineering warns. If there is one, the ATT/UMP consent flow also wants a port.
3. Is furniture moved by the player (19 B7 Layout; 15 "floor plan")? The answer determines baked lighting and the lightmap budget.
4. Is service only 120 real-time seconds, or is there a speed button? Pause is on the map, speed is not; it affects the fixed-step design.
5. Is the single source of localisation `localization/tr.json` (13 §File layout) or Unity Localization tables (19 §Packages)? I suggest JSON as the source with an editor import; Smart String will be needed for Turkish suffix agreement.
6. Is `hourSplit` or `arrivalWeights` canonical? 12 §5.6 writes it per cuisine.
7. Do downloaded cuisine packs carry rule JSON as well, or only art? The answer determines the "reject at start-up" policy and save-pack version compatibility.
8. Recipe units (13 §Pending decision 1): is the integer grams or portions proposal accepted? The fixed-point decision depends on it.
9. `IAnalytics` is in 04 §Ports and not in the 06 B2 summary; which list is current?
